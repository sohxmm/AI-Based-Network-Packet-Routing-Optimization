# AI-Based Network Packet Routing Optimization

A controlled benchmarking platform for congestion-aware routing. We implement
**eight routing strategies** — two exact classical solvers, a constraint-aware
classical baseline, one metaheuristic, three learned policies and a random floor
— and measure them head-to-head under **seven reproducible scenarios** with
quality-of-service constraints, statistical significance testing across
independent replications, fallback tracking and automated degeneracy detection.

The platform runs against a synthetic closed-loop simulator, a recorded trace, or
**live measurements of your own network**.

> **No GPU is required, for anything, including training.** Every model is small
> enough to train on a laptop CPU in minutes, and all trained checkpoints are
> committed — `docker compose up` gives you a working system with real models, no
> training step.

**On a single additive cost objective, no learned policy beats
congestion-weighted Dijkstra — and it cannot.**

That is not a limitation of our models. Dijkstra is *provably optimal* for any
additive, non-negative edge cost. A well-trained ranker must converge to it, and
ours does: the GNN reproduces Dijkstra's chosen path 96-98% of the time
on best-effort traffic, and our own degeneracy guardrail flags it for doing so.

Learned routing can only add value where the objective is **not** a single
additive sum. That is why this project has a QoS layer, a closed-loop simulator
and a cascading-failure scenario — they are the regimes where the question is
open.

### And in the QoS regime, the classical ceiling still wins

`qos_mixed_traffic` is the scenario built to leave the regime where Dijkstra is
optimal: five traffic classes, hard constraints on jitter, loss and bottleneck
utilization, a problem that is NP-hard in general. Constraint satisfaction rate,
by class, 15 runs:

| Algorithm | emergency | interactive | gaming | bulk | best-effort | overall |
|---|---|---|---|---|---|---|
| **Constrained** | **92.4%** | **97.1%** | **98.1%** | **99.9%** | 100% | **97.5%** |
| GNN | 82.3% | 94.2% | 96.2% | 99.3% | 100% | 94.3% |
| Dijkstra | 84.0% | 92.7% | 95.1% | 99.2% | 100% | 94.2% |
| RL (PPO) | 78.5% | 90.8% | 92.8% | 98.6% | 100% | 92.2% |
| Random | 61.7% | 80.8% | 87.0% | 96.0% | 100% | 85.4% |

Read the **emergency** column, not the overall one. `best_effort` has no hard
constraints, sits at 100% for everyone and drags the average together: the
overall spread is ~15 points, the emergency spread is ~31.

The classical `constrained` router — k-shortest paths filtered by feasibility —
wins every class, and pays 1.6% in mean latency to do it. **No learned router
beats it.**

This is not evidence that learned routing fails here, and we do not write it up
that way. It is a **training-objective gap**: the GNN was trained to rank paths
by additive cost and the PPO agent was rewarded for latency, so neither has ever
been asked to satisfy a constraint. They behave exactly as trained.

The honest summary of this project is that it **built the arena in which learned
routing could win, and has not yet trained a model that wins in it.** Closing
that gap — a feasibility term in the reward, a constraint-aware ranking loss — is
the most direct experiment we are leaving undone.

See [Limitations](#️-limitations-and-what-we-would-change).

### Running without Docker

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r service/requirements-dev.txt
python -m uvicorn service.main:app --reload --port 8000     # terminal 1

cd web && npm ci && npm run dev                              # terminal 2
```

The backend runs without PostgreSQL — history and metrics degrade to live-state
estimates and a warning is logged. Nothing else is affected.

> **The backend must run with a single worker.** `service/state.py` holds a
> module-level singleton network source; two workers would each own a divergent
> copy of the network and the dashboard would flicker between two realities. The
> Dockerfile pins `--workers 1` with a comment saying why.

starting a web server.

### The algorithms

| Name | Kind | Notes |
|---|---|---|
| `dijkstra` | Classical, exact | Optimal for additive cost. The baseline. |
| `bellman_ford` | Classical, exact | A correctness cross-check on Dijkstra, **not** an independent baseline — with identical non-negative weights they necessarily agree. |
| `constrained` | Classical, constraint-aware | k-shortest paths with feasibility filtering. The honest QoS *ceiling*. |
| `aco` | Metaheuristic | Ant Colony Optimization. Highest path diversity; ~10× the compute of everything else. |
| `gnn` | Learned | Edge-pooled graph neural network ranker, conditioned on traffic class. |
| `rl` | Learned | PPO over the candidate set. |
| `multi_agent` | Learned | Decentralized hop-by-hop policies, one per region, centralized critic. |
| `random_baseline` | Reference | Uniform over candidates. The *floor* — anything that does not beat it has not learned. |

### The traffic classes

| Class | Optimises | Hard constraints |
|---|---|---|
| Emergency | loss ≫ latency | path loss ≤ 1%, bottleneck ≤ 70%, ≤ 8 hops |
| Voice / video | latency, loss, jitter | loss ≤ 2%, bottleneck ≤ 80%, ≤ 8 hops |
| Gaming | latency | loss ≤ 4%, bottleneck ≤ 85%, ≤ 6 hops |
| Bulk | steered onto idle links | bottleneck ≤ 95% |
| Best effort | latency only | none |

The constraints are the point. Re-weighting an additive cost per class would
still be a problem Dijkstra solves exactly. Adding a **non-additive** bottleneck
constraint makes it a multi-constrained optimal path problem, which is NP-hard in
general — and constraint-blind Dijkstra will happily return an infeasible path.
The headline QoS metric is therefore **constraint satisfaction rate**, not
latency.

## Running against your own network

The platform does not require the simulator. `core/sources.py` defines three
interchangeable network sources.

### Replay a recorded trace

```bash
curl -X POST localhost:8000/sim/source \
  -H 'Content-Type: application/json' \
  -d '{"kind": "trace", "trace_path": "datasets/example_trace.jsonl"}'
```

JSONL or CSV; `queue_size` and `packet_loss_rate` are derived when absent, so a
trace only needs latency and utilization. A CAIDA, Mininet or NS-3 export
converted to either shape works with no code change. **We have not done that
conversion and no real trace is included.**

### Measure your own network, live

```bash
LIVE_PROBE_ENABLED=1 docker compose up
```

Then pick **Live** in the dashboard's *Network source* panel, or:

```bash
curl -X POST localhost:8000/sim/source \
  -H 'Content-Type: application/json' \
  -d '{"kind": "live", "targets": ["1.1.1.1", "8.8.8.8", "192.168.1.1"]}'
```

You get real RTT, jitter and loss per target, updating live, with utilization
estimated from RTT inflation over the best RTT ever observed for that path.

**Scope, stated plainly.** This is a read-only diagnostic. It sends one ordinary
ICMP echo per target per tick using the system `ping` binary — exactly what a
network engineer does by hand. It does **not** scan address ranges, enumerate
hosts, inject or forward traffic, and it never needs root. Targets must be listed
explicitly, and it will not start without `LIVE_PROBE_ENABLED=1`. **Only measure
networks you are authorised to measure.**

**And the honest limitation, which the UI also displays:** live mode produces a
*star* topology — one path per destination — so **routing algorithms cannot
differentiate on it**. It demonstrates real telemetry and congestion detection,
not routing quality. No number in this project comes from it.

To bridge the two, record what you measure and replay it deterministically:

```python
from core.sources import LiveProbeSource, record_trace
record_trace(LiveProbeSource(), steps=500, destination="datasets/my_network.jsonl")
```

## Reproducing our results

```bash
make bench     # ~25 min. Uses the committed checkpoints; reproduces the published numbers exactly.
make train     # ~35 min. Retrains everything from scratch; the learned rows will move.
make verify    # Asserts the documentation matches the artifacts.
```

**Trained weights are committed** (about 4 MB in total). This is a deliberate
departure from the usual advice, and the reason is the project's own history:
three of four AI features silently served heuristics for months because their
artifacts were missing or misnamed. Shipping them is what makes `docker compose
up` produce a working demo with real models rather than silent fallbacks.
`.gitignore` states this decision explicitly instead of contradicting itself, as
the previous one did.

Training times on 4 CPU cores, no GPU:

| Model | Time |
|---|---|
| GNN ranker | ~10 min |
| PPO policy | ~16 min |
| LSTM forecaster | ~30 s |
| Regional policies (×4) | ~10 min |

## ⚠️ Limitations and what we would change

- **The simulator is synthetic.** Every published number comes from
  `core/simulator.py`. Trace replay and live measurement exist; neither produces
  a benchmark result.
- **A good learned ranker on an additive objective converges to Dijkstra**, and
  our GNN does. That is optimality, not failure — and it means learned routing
  adds nothing in that regime.
- **No learned router beats the classical ceiling, even under QoS constraints.**
  `constrained` wins every traffic class. The learned routers were never trained
  to satisfy a constraint, so this is a training-objective gap rather than a
  verdict on the approach — but it is where the project currently stands.
- **PPO does not beat greedy.** 0.867 against 0.903.
- **PPO cannot run on a topology it was not trained on.** Its observation is a
  fixed-width vector, so on the 100-node scenario and on any scenario with links
  removed its fallback rate is **1.00**: not one decision came from the trained
  policy. It detects the mismatch, falls back, and the results say so — but it is
  not fixed. Replacing the flat observation with the GNN's node embeddings would
  fix it; the GNN has no such problem and runs on 100 nodes with zero fallbacks.
- **Bellman-Ford returns an identical path to Dijkstra** in effectively 100% of
  trials. It is a correctness cross-check, not a second baseline.
- **Nothing learns online.** All models are trained offline and frozen. The
  original problem statement asks for a system that "continuously learns network
  conditions"; that is not delivered and was explicitly de-scoped. A serve-time
  contextual bandit over the candidate set is the obvious next step.
- **The QoS oracle is greedy**, not globally optimal — it ignores the downstream
  consequences of its own load.
- **The container stack was not executed by us.** No Docker daemon was available
  in the final build environment. The Dockerfiles, compose file and CI smoke job
  are written and reviewed, but running `make up` should be your first check.
- **Sample sizes are modest**: 15 runs × 40 steps × 8 demands per scenario.

## A note on how this project is presented

This codebase was rebuilt after a review of our own work found that three of
its four AI features had never actually run, that the reinforcement learning
agent had provably not learned, and that our own benchmark showed the AI losing
in every scenario while saying so nowhere in the documentation.

The sharpest problem was not any individual defect. It was that the *disclosed*
problems were all small while the *undisclosed* ones were all large — which
leads a reader to conclude the disclosure was managed rather than honest.

So: the limitations section above is not a formality, the guardrails that flag
our own models as degenerate run in CI, and `make verify` fails the build if
anything in this README stops matching the artifacts in the repository. A
rigorous negative result with a correct causal explanation is a better project
than a positive one you cannot defend.
